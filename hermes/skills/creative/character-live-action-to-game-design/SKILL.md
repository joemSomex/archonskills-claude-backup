# Character: Live action to Game Design

## When to Use

When the user sends or explicitly invokes `Character: Live action to Game Design.` alongside one image, treat that image as `@image1` and immediately execute the ten-variation generation workflow without asking for confirmation. A mention of the trigger in a user request with an attached image is sufficient; do not stop at restating the phrase or describing the skill. This is an image-generation task, not a prompt rewrite. If the phrase is only discussed or quoted as a skill-design instruction without a new image-generation request, explain or update the skill instead. If the assistant invokes the trigger as part of carrying out a user-provided image task, proceed with generation rather than stopping at the invocation. An unrelated assistant quotation of the trigger does not independently create a new user request. If no image accompanies the user's invocation, ask for it; do not silently reuse an older attachment.

**Before generating, read `references/generation-brief.md` in full.** It is the user's authoritative brief. Send its substantive visual requirements to the image generator, not a short agent-authored substitute. Preserve generic-character logic: infer identity, presentation, age impression, hair, clothing, and palette from the current input, not a past example. An explicitly requested eye-color or other character change overrides only that one source attribute; without an override, retain the source. For a source contact sheet with a missing/cut-out head in one full-body panel but a visible face in another, reconstruct the visible face in the front view; do not mistake the cut-out for a mask. Preserve a genuine mask or face covering when it is actually worn. The user's preferred look is dimensional **painterly animated character art**, with designed facial planes, graphic hand-painted transitions, and expressive but recognizable identity. It need not look like a literal game-engine mesh or plastic 3D asset. Do not transfer any sample character's gender, eye color, costume, or face to future characters.

**Provider lock:** Use ChatGPT/OpenAI image generation only for this workflow. Never delegate image generation to Claude, and never invoke Higgsfield MCP tools. On every new or resumed run, re-read this provider lock before any upload or generation; if an earlier run used Higgsfield, do not continue, poll, display, or deliver its jobs. Restart from the original attachment through the OpenAI image tool. If the OpenAI image-generation path is unavailable or fails after reasonable retries, report the blocker instead of silently switching providers. If the OpenAI image tool reports `auth_required` while `hermes auth status openai-codex` still says logged in, refresh the existing credential with `hermes auth refresh openai-codex` and retry the same image once before treating it as blocked; never switch to Claude/Higgsfield. This workflow does not require a pre-generation approval step.

1. Inspect the actual attached image at useful size and map the visible face/identity, outfit construction, material palette, full-body proportions, and any intentional covering. If the input is a contact sheet, use its portrait and full-body views as identity and costume evidence; the output is still ten separate three-view sheets. If the source is fully nonhuman and sealed, translate facial-plane/hair variation directions into helmet planes, cable grouping, armor light/shadow and material rendering; preserve actual markings and visible back hardware, and never invent a human face, eyes, hair or props carried over from an unrelated prior edit. If the CURRENT source already shows held props, preserve their design and handedness consistently in front/back despite the generic brief's empty-hand composition; do not import accessories from a previous source. For a mechanical photo-source, check the first render at thumbnail size: if it reads as an unchanged photograph with a painted background, explicitly re-illustrate matte armor and mechanical shadows with designed brush-shaped planes before batching.
2. **Default to the full first batch of ten independent generations** when the original and brief are clear. The user usually gets good results from a first batch and does not want a mandatory one-image calibration to slow it down. Lead each call with the complete brief's painterly animated finish rather than reducing it to '3D maquette', 'virtual puppet', 'solid clumps', or 'game-engine render'. The visual benchmark is the user's approved sample: soft neutral studio background, two full-body views at left and center, large right portrait, natural proportions, visibly painted tonal planes across the face, graphic yet natural hair, and detailed worn fabric; its red eyes were a one-off explicit override, **not** a default.
3. Generate each named variation afresh from the same **original** `@image1`; never use a preceding variation as input to another. Send the shared full brief plus one variation-specific direction on each call, preserving any explicit user override and resolving its conflicting source-lock clause. Make exactly one standalone 16:9 three-view sheet per generation: left complete back view, center complete front view, right large head-and-shoulders portrait. If the user explicitly requires the character riding or operating a vehicle in the image, this overrides the standing/empty-hand and isolated-portrait defaults: show the character actively operating the same complete source vehicle in the two wider views and still visibly on the vehicle with controls/fairing in the close view. Lock source vehicle morphology and markings; do not silently omit it to satisfy the generic character-sheet layout. If the user then says to match image 1's layout, inspect whether image 1 is a SINGLE side-profile hero composition rather than a sheet; reproduce its one-rider/one-vehicle orientation, scale, framing and backdrop per file instead of persisting with the three-view template. Keep the light neutral backdrop, camera scale, light direction, identity, outfit, and palette consistent. **If the initial batch reveals a shared style or composition error, switch to one generation at a time:** correct and inspect a single image internally, then resume only once the issue is resolved. Do not make the user approve a calibration unless they request it. If a mechanical photoreal source keeps anchoring generations to near-identical glossy renders despite painterly prompts, do not count unique hashes or painted backgrounds as success. Before retrying a batch, make one abstract matte armor/red-cable material-and-brushwork swatch with OpenAI (no character), use that as the style-only `image_url` and include the CURRENT original source in `reference_image_urls` for identity/structure only; generate one sheet and compare native-size armor rendering to the initial draft. Explicitly forbid the swatch's dark/textured background and broad accent-color stains when the source calls for a pale studio and restrained accents; otherwise the style input can hijack setting and palette. Never feed a prior character variation as the character source. For a semi-human or biomechanical source whose face and armor remain photoreal after the abstract material-swatch retry, make one generic original hand-painted face-and-shoulders style study with deliberately different hair, clothing, and eye design. Use that study as style-only `image_url`, the CURRENT source as identity/geometry `reference_image_urls`, and explicitly forbid transfer of the study's face, hair, two-eye layout, clothing, or background. Calibrate one sheet and require broad intentional brush-shaped planes on both the face and armor at thumbnail size before regenerating the rest; a material swatch alone may not steer portrait rendering. Never use an earlier character variation as the style or identity input. When a glossy CGI source keeps anchoring the armor to near-photographic rendering, an abstract armor-material swatch may repeat the problem. Try a nonfigurative matte-gouache swatch made of broad opaque charcoal paint shapes on a light ground (no character or armor object), use it as style-only `image_url` and the CURRENT original as the sole character `reference_image_urls`; calibrate one sheet. Explicitly lock curved source plates and shoulder silhouette so the abstract swatch transfers paint treatment, not cubist geometry, extra red bands, or brush strokes onto the studio background. Compare both the painted finish and garment construction at full size before batching. If reasonable OpenAI attempts still fail, say so and share only clearly labeled drafts, not ten purported successes.
When the user corrects machine width/height, prioritize the original chassis width-to-total-height ratio, crouched stance, shoulder span, leg lengths and foot spread over sheet packing or animation exaggeration. Regenerate directly from the original with matching front-view perspective; allocate more page width to full bodies instead of narrowing them to enlarge the portrait. On rear views, show closed pod backs rather than repeating forward-facing circular apertures. Do not claim pixel-exact geometry preservation from generative redraws.

4. Check each output visually against the original, the complete brief, and the painterly-style benchmark: designed dimensional facial shading rather than realistic photo skin or overly simplified plastic sculpt; recognizable face and hair; costume, material, asymmetry and palette fidelity; consistent views of one design; both full-body heads and footwear inside the frame; no added props, text, logos, borders, or variant collage. For a front-only sealed mech reference, explicitly verify that LEFT is truly dorsal: rear helmet has no frontal optic, rear scapula/spine replaces front chest or breast plates, and heel backs differ from the front; two front-looking figures do not satisfy the requested back/front sheet. Regenerate failed slots independently from the original. Different file hashes do not establish meaningful visual variation; compare all ten side by side before delivery.
5. Save each accepted result as its own PNG file. Verify exactly ten files, their PNG encoding, 16:9 pixel dimensions, and distinct hashes programmatically; inspect a labeled contact sheet for meaningful visual differences. Inspect the actual decoded dimensions rather than trusting the tool's landscape label: OpenAI can return a near-16:9 raster such as 1672×941. If all character details already fit, add minimal neutral padding to an exact 16:9 canvas (for example 1680×945) without resampling, cropping or stretching geometry, and record original dimensions and padding in the manifest. Padding cannot recover already cropped teeth or boots; regenerate those failures. Deliver the ten individual PNGs in chat, not the contact sheet as a substitute. If visual criteria remain unmet, do not label the batch completed. These are 2D images of a character design, not actual editable 3D models. A ChatGPT conversation model/effort setting (the user cited Sol 6.1, Pro Effort) does not prove which image backend was used; never promise identical rendering or claim to have selected that setting unless the available tool explicitly supports and confirms it.
