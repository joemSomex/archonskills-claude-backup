# Pixel-art forum utility buttons

## Procedure

1. Inspect the reference for letter construction, foreground/background contrast, button height, border weight, bevel direction, corner steps and pixel-cluster scale. Separate literal copy from reference-only labels; keep the requested word exact. When a new style sheet replaces glossy colored keys with monochrome speech bubbles, rebuild the visual grammar as white interiors, thin black stepped outlines, a connected lower-left tail and a hard offset gray shadow; do not merely desaturate the old beveled button. Map each later attachment to its literal label and export one result per source. Render simple speech-bubble geometry and bitmap capitals on an integer grid, then enlarge with nearest-neighbor so the requested high-resolution canvas has crisp intentional pixel edges rather than blurred interpolation. Fit the bubble width to each word while keeping letter scale, face height, outline and shadow offset consistent.
2. Use Pillow RGBA drawing on an integer working grid for simple pixel UI. For a 500 x 500 export, a 125 x 125 working canvas enlarged fourfold with `Image.Resampling.NEAREST` provides crisp controlled clusters. This is a useful construction scale, not a required grid for every reference.
3. Define each needed glyph as a bitmap or use a verified pixel font. Compute text width as `sum(glyph_widths) * scale + gap * (len(text) - 1)`, then derive button width from that measurement and fixed horizontal padding. Keep height, glyph scale, baseline and border weight consistent across the set. Center by measured glyph bounds rather than character count. Parameterize label, palette, bounds and decoration anchors instead of globally replacing coordinates or scale constants in an earlier script: a longer word can run under highlights that were safely beside a short label. Derive left/right details from the current face bounds and reserve an expanded text rectangle, including its shadow, as a decoration exclusion zone.
4. Reserve distinct macro constructions before drawing the batch. Raised bevel, pressed inset, chamfered chassis, stepped plate, separated corner clamps, double rail and notched enclosure are structural alternatives; one outline in five palettes is only a color study. Retain the current palette direction when the user narrows a previous multicolor set to one hue.
5. Draw each image independently in this order: transparent canvas, any bounded shadow, silhouette/background, bevel and structural borders, low-contrast texture, decorative hardware, then lettering. Keep all decoration and scanlines behind or outside the glyph mask so they cannot break letter strokes. Pass colors explicitly in reusable drawing helpers, because loop-captured/default colors can silently carry a prior palette into a later variant.
6. Render decorative micro-lines sparingly and preserve negative space around text. A request for a more decorative button authorizes frame detail, not unrelated characters, scenery, logos or symbols. Use a lighter same-family text tone when necessary to keep dark red or violet designs readable. For a chunky glossy arcade reference, build a dark outer silhouette, a visible lower wall about 4-7 working pixels deep, a stepped face, three or four discrete material-color bands, a narrow bright upper rim and a short broken specular cap. Use high-contrast cream bitmap lettering; add an offset shadow only when counters and inter-letter gaps remain visibly clear at small display size. Do not widen glyph strokes to imitate a bold reference without reserving extra tracking: adjacent strokes and their shadows can visually merge even when the underlying glyph masks are separate. Keep gloss highlights above the text rather than through it; drawing a highlight first does not prevent it from reading as an extra letter stroke through a glyph counter. Vary corner steps, sidewall depth, inset framing and rim construction across the batch, not only the fill hue.
7. When the user explicitly requests independent model generations rather than deterministic designs, generate each reserved construction from the original UI style reference with the exact label repeated in every prompt. Request only geometric rim decoration and reflections, not the reference sheet's icons or unrelated labels. If a generated horizontal button arrives on a wide rather than square raster, extract its complete silhouette first, uniformly fit it into the requested square transparent canvas, and center it without stretching; the generated raster's aspect ratio need not become the export's aspect ratio. Choose a flat key absent from every button material, sample its actual RGB, and preserve dark violet paint when removing bright magenta. For a single contiguous button, the largest non-key component can reject background flecks, but inspect all bevels and any intentionally separate hardware before discarding other components. Read the complete generated label visually before accepting it, because a prompt containing exact spelling does not verify the output.
8. Export separate exact-size PNGs. Reopen every image and verify RGBA mode, requested dimensions, alpha extrema including zero and full opacity, transparent corners, exact file count and distinct hashes. Compare silhouettes as well as hashes to prove structural variety.
9. Inspect all wording at native size and representative small forum size on both light and dark mattes. Reject missing strokes, unintended stencil cuts, illegible counters, clipped border details, off-center labels and oversized empty padding that makes the active button too small. A contact sheet is internal QA, not the requested standalone delivery.

## Typography-only revision and font exploration

1. Use the user's attached button as the immutable base. Inspect its actual RGBA pixels, sample the flat face color beside the letters, and isolate the complete old glyphs with a spatially bounded color mask. Restore only those glyph pixels from the verified flat face color or a clean pre-typesetting layer; do not repaint the whole face or rebuild the frame.
2. Separate spacing studies from font studies. For a congestion correction, compare narrower glyphs, wider tracking, a larger word gap and shadow removal while retaining a common frame and palette. For unique font variations, change letter skeletons, counters, terminals, weight or serif construction: block arcade, rounded pixel, slab serif, local-bridge stencil and condensed terminal are distinct directions, whereas five tracking values are not five fonts. Label custom bitmap directions descriptively, not as licensed font families.
3. Measure complete word widths including a dedicated word gap and horizontal padding. Center the combined glyph bounds in the usable face, not the outer sidewall silhouette. Measure the final ink bounding box after every weight change: set its origin from `face_center - ink_size / 2` on the integer working grid and verify its center within one working pixel of the intended face center. Reserve distinct glyph tracking and word spacing before boldening; do not grow the entire lockup until neighboring strokes merge. Keep stroke weight readable rather than making an entire batch hairline-thin to cure congestion. Do not let decorative stencil bridges turn O into A or N into H; reject any ambiguous word at small display size.
4. Typeset every variant independently over the cleaned original. Resize only the transparent lettering overlay with nearest-neighbor integer scaling; retain the source button pixels and alpha. Verify `source_alpha == output_alpha` and zero changed decoded pixels outside the union of old and new glyph masks. A palette-wide mask alone is insufficient when highlights elsewhere share the lettering color; constrain it to the text area.
5. For a boldness-only revision on a flat white speech bubble, segment dark glyphs inside a measured text strip that excludes the outline and tail. Dilate only that mask with `ImageFilter.MaxFilter(3)` or `MaxFilter(5)` at final resolution, starting with the smaller growth and inspecting counters and gaps. Intersect the added ink with verified opaque white interior pixels, then assign the sampled original ink RGB only to those pixels. A 5-pixel maximum filter grows each edge by two pixels; on an original six-pixel stroke this yields roughly ten-pixel strokes but also shrinks a six-pixel gap to two. Reduce dilation or rebuild the glyphs with more tracking if counters close. Never filter the full artwork: dark outlines and the gray shadow would also expand. Assert byte-identical alpha and zero decoded differences outside the added-ink mask.
6. Inspect every label in two small-size views: the complete square uniformly scaled to the intended CSS/icon dimensions, and an aspect-preserving tight crop of the occupied badge scaled to the intended badge width. Never resize a crop to independently chosen width and height, because that distorts glyph proportions and can give misleading legibility results. Check native crops and light/dark mattes too. Use nearest-neighbor for final integer-grid pixel-art enlargement; a high-quality downsampler is appropriate for simulating browser reduction in QA. Deliver only the requested standalone transparent PNGs and brief labels, preserving established dimensions unless the user changes them.

## Delivery

Attach each accepted PNG separately with a short statement of size and transparency. Describe deterministic renders as created designs, not as model generations or pixel-identical copies of a reference font. Keep preview sheets internal unless requested.
